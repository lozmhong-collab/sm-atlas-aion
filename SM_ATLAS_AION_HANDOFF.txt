- nul 같은 Windows 예약 이름을 일반 Win32 경로로 조회하면 os error 1이 발생하고, 기존 AionCore는 자식 하나의 정보 조회 실패로 전체 폴더 목록을 실패시켰다.
- AionCore v0.2.2 (47e66d0d151123e973b3fd1e77afcb5671b3f8c5) 기반 패치를 packages/shared-scripts/src/aioncore-patches/windows-reserved-paths.patch에 포함했다.
- 파일 입출력과 감시 경계에서 확장 Windows 경로를 사용한다. 일반 드라이브·UNC·한글/공백 경로를 지원하며 기존 file: URI와 프로젝트 식별자 형식은 유지한다.
- 자식 하나의 메타데이터 조회 실패는 로그를 남기고 건너뛰어 나머지 파일 목록을 보존한다. 폴더 자체의 조회 오류는 계속 실패로 전달한다.
- explorerStore.ts는 조회 실패 및 부분 응답에서 빠진 폴더를 화면에 알린다. 이전 정상 목록은 유지하고, 최초 구독 실패도 새로고침/재시도로 복구한다. 오래된 프로젝트/요청 응답은 반영하지 않는다.
- ExplorerPanel.tsx에는 13개 언어의 오류 안내와 재시도 버튼을 추가했다. 서버의 내부 오류 원문·개인 경로를 그대로 화면에 노출하지 않는다.
- Windows 빌드 진입점은 패치된 AionCore를 선택한다. 수정 전 GitHub 릴리스 실행 파일이 다시 다운로드되어 패치를 덮어쓰지 않는다.
- Windows x64용으로 직접 빌드한 백엔드 압축본도 같은 폴더에 포함한다. 빌드 도구가 압축본·실행 파일·패치 해시를 검증해 사용하므로 일반 x64 설치기 빌드에는 Rust가 필요하지 않다.
- 회사 AionCore에 별도 소스 수정이 있다면 AIONUI_BACKEND_SOURCE_DIR로 해당 체크아웃을 지정한다. 회사 변경을 reset/clean하지 않고 호환 패치를 확인·적용한 뒤 빌드한다. 이 경우 Rust 1.95.0와 MSVC/Windows SDK가 필요하다.
- AIONUI_BACKEND_LOCAL_BINARY/LOCAL_BUNDLE_DIR를 직접 지정하면 새 실행 파일 옆의 aioncore.exe.atlas-patches.json도 함께 전달한다. 패치·실행 파일 해시와 아키텍처가 다른 입력은 패키징하지 않는다.
- 사용자 폴더의 nul 파일을 삭제해 해결하는 방식이 아니다. 기존 파일과 회사 CA·프록시·CLI·인증·설치기 설정을 유지한다.
- renderer만 다시 빌드해서는 백엔드 수정이 반영되지 않는다. 이 소스를 병합하고 실제 설치 EXE에 새 AionCore까지 포함해 다시 빌드한다.
- AIONUI_BACKEND_BIN으로 실행 파일 경로를 별도로 지정한 회사 실행/테스트 환경에서는 이전 백엔드를 계속 가리키지 않는지도 확인한다.
- 수정 전 Rust 테스트에서 실제 nul 파일의 메타데이터 조회가 os error 1로 실패하는 것을 재현했다. 수정 후 예약 파일 읽기·쓰기·이름 변경과 aux 하위 폴더 조회, 드라이브·UNC·한글 경로 검사가 통과했다.
- 실제 Electron 앱과 새 번들 백엔드의 Windows E2E 2개가 통과했다(55.4초). nul/con.txt/aux/README 동시 표시, 하위 폴더 확장, 새로고침, 최초 조회 실패 안내와 재시도 후 실제 파일 복구를 확인했다. 사용자/회사 서버에 모델 요청을 보내지 않았다.
- AionCore 프로젝트 크레이트 검사: 수정 전 원본은 337개 통과·24개 실패, 수정 후는 339개 통과·동일한 24개 실패이다. Windows에서 Unix 경로 fixture를 사용하는 검사, inode 기반 모의 rename 검사, Git 줄바꿈 기대값이 실패하며 새 실패는 없었다. 이 결과를 백엔드 전체 검사가 모두 통과한 것으로 표현하지 않는다.
- AionCore 프로젝트 크레이트의 clippy(all targets, warnings as errors)와 패치된 전체 백엔드 release 빌드는 통과했다.
- AionCore 전체 workspace 검사도 완료했다: 9,231개 통과·89개 실패·53개 건너뜀, 실패 대상 18개이다. Windows에서 실행 파일을 찾지 못하는 셸 fixture, Unix 경로/구분자·줄바꿈·스킬 front matter 기대값 등의 실패가 포함된다. 전체 원본 workspace와의 실패 비교는 하지 않았으므로 89개가 모두 기존 실패라고 단정하지 않는다. 이 변경은 전체 백엔드 회귀가 전부 통과한 상태는 아니다.
- 전달 TXT를 새 폴더에 복원해 2,368개 파일의 원본 바이트 일치, 10개 분할 TXT의 재결합, 내장 복원 도구를 확인했다. 복원한 백엔드 압축본을 Rust 빌드 없이 풀어 실제 앱에서 검증한 실행 파일과 동일한 SHA-256임을 확인했다.
- 데스크톱 최종 전체 검사: 5,180개 통과·미리보기 모듈 cold import 시간 초과 3개·기존 6개 건너뜀이다. 해당 PreviewPanel/OfficeWatchViewer 두 파일을 단독 재검사해 17개 모두 통과했다. 파일 탐색기 회귀 56개와 실제 Windows 앱 E2E 2개도 통과했다.

8. 회사의 실제 도구 이름·입력·응답, 페이지 ancestors/version 및 동시 수정 동작이 다르면 해당 adapter/codec만 보완한다.
   미리 모든 미확인 항목의 답을 기다리며 구현을 멈출 필요는 없다. 실제 실패/차이가 확인되는 지점부터 수정하고 결과를 보고한다.

구현된 사용 흐름
1. 사이드바의 "프로젝트 추가"로 실제 작업 폴더를 등록한다.
2. 세션이 없는 폴더도 프로젝트 목록에 남는다. 목록과 마지막 선택 경로를 별도로 저장한다.
3. 프로젝트의 + 또는 상단 "새 세션"으로 해당 폴더에서 새 세션을 만든다.
4. 새 세션 화면에서 프로젝트와 사용할 Claude/Codex 등을 선택한다.
5. 빈 세션을 만들거나 첫 요청을 입력한다. 각 세션은 서로 다른 conversation ID와 독립 이력을 가진다.
6. 기존 세션을 선택해 전환하고, 선택한 프로젝트 경로에서 다음 세션을 시작한다.
7. 빈 프로젝트의 등록을 해제하면 선택 경로도 정리한다. 실제 폴더와 파일은 삭제하지 않는다.
8. 기존 사용자 지정 workspace의 세션도 프로젝트 아래에 모은다. 팀 소속 세션은 분리한다.

복원 방법
전체 TXT를 AI 대화에 한 번에 붙이지 말고, 먼저 이 안내와 복원 도구만 읽는다.
SM_ATLAS_AION_SOURCE.txt의 RESTORER_SCRIPT_BEGIN과 RESTORER_SCRIPT_END 사이를
restoreBundle.mjs로 저장한다. 마커 줄 자체는 저장하지 않는다.
복원 도구는 데이터를 검증하고 파일을 쓰며, 복원한 코드를 자동 실행하지 않는다.

Node가 준비된 환경에서:
  node restoreBundle.mjs "SM_ATLAS_AION_SOURCE.txt" --verify
  node restoreBundle.mjs "SM_ATLAS_AION_SOURCE.txt" --list
  node restoreBundle.mjs "SM_ATLAS_AION_SOURCE.txt" --restore "C:\work\sm-atlas-project-sessions-NEW"

복원 대상은 아직 존재하지 않는 새 폴더여야 한다.
위 예시의 실제 프로젝트는 C:\work\sm-atlas-project-sessions-NEW\sm-atlas-aion 이다.
복원 후 AGENTS.md, CONTRIBUTING.md 및 회사 환경 가이드를 읽고 작업한다.
분할본을 받았다면 SM_ATLAS_AION_PARTS.txt의 번호 순서와 SHA-256을 확인하고,
모든 part TXT를 바이트 그대로 합친 뒤 전체 TXT를 검증·복원한다. 조각을 편집기로 재저장하지 않는다.
